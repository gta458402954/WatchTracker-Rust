# WatchTracker 恢复运行与功能改进需求

## 1. 项目背景

当前项目的首要问题不是继续增加功能，而是先确保它能在目标 Windows 环境中稳定安装依赖、启动、读写数据、完成核心操作并成功构建。任何新增功能都不得优先于阻塞正常运行的问题。

项目恢复到可正常使用的稳定基线后，再完成地区分类动态化重构：将地区识别统一到 ISO 3166-1 alpha-2 国家代码，并在不破坏旧数据的前提下，根据用户实际拥有的影视记录动态生成地区筛选项。

当前工作区可能已经包含本需求的部分实现、修复代码、测试和未提交修改。执行者必须先审查现有实现，判断哪些要求已经满足，不得从头重写、覆盖或重复实现；只有经过实际验证的内容才能标记为已完成。

`REMAINING_ISSUES.md` 是前一轮审查、整改进度和历史测试结果的输入材料。Codex 和 Antigravity 必须读取其中的已知问题，但不得把文档中的历史“已通过”结论直接继承为本轮验收结果；所有相关结论都必须基于当前代码和当前环境重新验证。

## 2. 项目目标

目标按以下顺序执行，前一阶段未通过验收时不得用后续功能掩盖或绕过问题：

1. **P0：恢复正常运行。** 项目能够在 Windows 开发环境中安装、启动 Tauri 桌面应用、初始化或升级数据库、读取现有记录并完成核心增删改查。
2. **P0：建立稳定基线。** 前端构建、TypeScript、ESLint、Vitest、Playwright 和适用的 Rust 检查通过；若仍有非阻塞问题，必须明确记录。
3. **P1：完成地区动态化。** 以 TMDB 返回并保存到 `originCountry` 的 ISO 国家代码作为首要数据源，动态生成地区筛选项，并兼容旧数据。
4. **后续阶段：按路线图迭代。** 同步冲突、观看日志等新增能力在稳定基线和地区专项完成后另行立项。

## 3. P0 正常运行基线

“项目能正常跑起来”必须同时满足本节要求，不能仅以 Vite 页面能够打开作为完成依据。

### BR-01 环境与依赖

1. 在目标 Windows 环境中，Node.js、npm、Rust、Cargo 和 Tauri 所需系统依赖能够被正确识别。
2. 从仓库现有锁文件安装前端依赖成功，不依赖未记录的全局包或开发者机器上的私有文件。
3. Rust 依赖能够解析和编译；所需最低版本、环境变量和系统前置条件应在 README 中写明。
4. 缺少可选凭据（例如 TMDB、WebDAV）时，应用仍应能够启动并使用本地核心功能，不得白屏或直接退出。

### BR-02 启动与界面

1. `npm run dev` 能启动前端开发服务器，页面无阻塞渲染的致命错误。
2. `npm run tauri dev` 能启动 Windows 桌面应用并进入主界面。
3. 首次启动、已有数据启动和数据库升级三种场景均不得出现崩溃、白屏或无限加载。
4. 启动期间的可恢复错误应给出可理解的提示；诊断信息应写入日志，不能只依赖开发者控制台。
5. 应用初始化必须明确区分 `loading`、`ready` 和 `error` 状态；加载失败不得显示成“暂无记录”，必须显示错误说明和重试入口。
6. 新增、编辑、删除、导入、恢复和同步等异步操作失败时，应通过统一的用户可见反馈显示，不能只写入 console。

### BR-03 数据与核心流程

1. 应用能够创建或打开本地 SQLite 数据库，并安全执行现有数据库迁移。
2. 已有影视记录能够加载和显示，不因字段缺失、旧格式或单条脏数据导致整个列表不可用。
3. 新增、查看、编辑和删除影视记录均可正常完成，重启应用后数据仍然一致。
4. 搜索、影视类型、观看状态、地区、评分、锁定状态和排序等现有核心交互可以组合使用。
5. 设置能够读取和保存；导入、导出、备份、恢复及 WebDAV 同步至少不得破坏本地数据。
6. TMDB 或 WebDAV 网络不可用、凭据缺失或请求失败时，应可恢复并保留本地数据。
7. 对数据库结构、导入或同步逻辑进行修复前，应保护现有用户数据；可能产生破坏性影响的修复必须提供备份或恢复路径。
8. 所有数据库迁移、导入、恢复、同步和破坏性场景测试必须使用临时数据库、测试夹具或真实数据库的独立副本，不得直接修改、清空或覆盖用户正在使用的数据库。
9. 使用真实数据库副本进行测试前，必须建立可恢复备份，并在执行日志中记录源路径、测试副本路径、备份位置和恢复方法；日志不得暴露凭据或不必要的个人数据。
10. 每个数据库 migration 的结构变更、数据变换和 `db_version` 更新必须位于同一个 SQLite 事务中；任意步骤失败时必须整体回滚，应用重新启动后能够安全重试，不得出现结构已经改变但版本号未更新的半迁移状态。
11. 设置项不存在与数据库查询失败必须严格区分；只有确实不存在的 setting 可以转换成“无值”，数据库损坏、类型错误、锁定和其他查询错误必须向上传递并留下诊断信息。

### BR-04 构建与可交付产物

1. 前端生产构建成功。
2. Tauri/Rust 后端检查与测试成功。
3. `npm run tauri build` 能生成可运行的 Windows 构建产物；若受签名、安装器或机器环境限制，必须区分代码问题和环境问题并提供证据。
4. 构建产物能够启动、创建或读取数据目录，并完成最小核心流程冒烟测试。
5. README 中的安装、开发启动、生产构建和数据目录说明与实际行为一致。
6. 数据库、日志、海报、备份和 `poster://` 协议必须遵循同一套应用数据目录解析规则；便携模式和系统 app-data 回退行为必须一致、可测试，并与 README 完全一致。

### BR-05 修复原则

1. 先复现和记录阻塞问题，再实施最小范围修复。
2. 不以删除用户数据、跳过数据库迁移、关闭类型检查或禁用测试作为修复手段。
3. 不顺带重写与故障无关的模块；现有未提交修改属于用户数据，必须保留。
4. 每个关键修复应有相应测试或可重复的验收步骤，防止问题再次出现。
5. 无法在当前环境验证的项目必须明确标记为“未验证”，不得推断为通过。
6. `docs/REFACTOR_ATOMIC_API.md` 必须按照当前真实实现重写，不得继续描述已经弃用的旧 IPC；文档至少应覆盖当前 DTO 和命令、generation、commitId、事务不变量、错误语义、stale snapshot、安全重试、恢复流程，以及 WebDAV PUT 与本地 SQLite 无法组成分布式事务的限制。
7. 项目不得提交一次性修复脚本、构建缓存、`playwright-report/`、`test-results/` 或其他本地测试产物；需要长期保留的维护脚本必须有明确名称、用途说明和可重复执行方式。

### BR-06 原子写入契约与系统字段

1. 记录更新接口只能接受允许修改的业务字段。
2. `id`、`createdAt`、`updatedAt`、`rev` 和 `revActor` 等系统字段不得由任意 IPC 调用方直接修改。
3. `updatedAt` 必须由 Rust 数据库事务生成，不得依赖前端设备时间。
4. 空更新必须采用明确且可测试的契约；推荐拒绝并返回可识别的参数错误，不得静默推进 generation 或修改系统时间。
5. 无法安全转换的数字、数组、对象以及未知字段必须被拒绝，不得静默转换成 SQL `NULL`。
6. 参数验证失败、记录写入失败或后续 setting 写入失败时，record、同 ID Tombstone、generation 和相关 setting 必须全部保持原样。
7. 更新不存在的记录必须返回可识别错误，且不得清除预先存在的 Tombstone 或产生任何部分写入。

## 4. 地区专项：名词与数据约定

- **标准国家代码**：优先遵循 ISO 3166-1 alpha-2 的两位大写代码，例如 `CN`、`US`、`JP`、`GB`。
- **兜底两位代码**：格式满足两个英文字母、但尚未配置中文名称或暂时无法确认分配状态的代码；规范化后保留并直接显示大写代码，以免静默丢失原始地区信息。
- **地区名称**：国家代码在界面上的本地化名称，例如 `CN` 显示为“中国大陆”。
- **旧地区标签**：旧版本保存在 `contentTags` 中的地区名称，例如“美国”“韩国”“中国香港”。
- **未知地区**：既没有可用 `originCountry`，也无法从旧地区标签识别国家或地区的记录。
- **多国作品**：`originCountry` 中包含两个或以上国家代码的记录，例如 `FR, DE`。

地区判断遵循以下优先级：

1. 优先读取并规范化 `originCountry`。
2. 仅当 `originCountry` 缺失、为空或没有任何可识别值时，才从 `contentTags` 中解析旧地区标签。
3. 两个来源均无法识别时，将记录归入“未知地区”。

## 5. 地区专项：功能需求

### FR-01 国家代码规范化

1. 国家代码在内部统一使用两位大写形式，自动清理首尾空白。
2. 支持英文逗号和中文全角逗号分隔的历史数据。
3. 同一记录中的重复国家代码应去重。
4. 英国的标准代码统一为 `GB`；旧数据中的 `UK` 必须在读取和筛选时兼容并规范化为 `GB`。
5. `CN`、`HK`、`TW` 必须保持为三个不同的代码，不得合并。
6. `N/A`、`NA`、`NULL`、`UNKNOWN`、空字符串以及不满足两个英文字母格式的内容均视为无效占位或脏数据，不得作为地区选项。
7. 对满足两个英文字母格式、但尚未配置中文名称或暂时无法确认分配状态的代码，应保留规范化后的大写代码作为兜底显示，不得静默丢失记录的地区信息。

### FR-02 地区名称显示

1. 常见 ISO 国家代码应显示对应的中文名称。
2. 以下名称必须固定显示：
   - `CN`：中国大陆
   - `HK`：中国香港
   - `TW`：中国台湾
   - `GB`：英国
3. 中国大陆、中国香港和中国台湾必须分别统计、分别展示、分别筛选。
4. 未配置中文名称的有效代码直接显示其大写代码。
5. 无国家信息的记录统一显示和筛选为“未知地区”。

### FR-03 动态生成地区筛选项

1. 地区筛选项不得再依赖写死的固定地区集合。
2. 筛选项应由当前已加载的影视记录聚合生成，并随记录的新增、编辑、删除、导入或同步结果更新。
3. 在当前影视类型和观看状态范围内数量为 `0` 的地区不得显示。
4. 切换影视类型或观看状态后，地区选项及数量应同步更新。
5. 地区选项的基础集合及数量只受当前影视类型和观看状态影响；评分、关键词搜索、锁定状态、排序方式和当前地区选择均不得改变地区选项的基础集合及数量，避免筛选项在交互过程中跳变。
6. 当前已选地区不得影响其他地区选项的统计；再次点击已选地区应取消该地区筛选。
7. 当数据更新导致当前已选地区不再存在时，应清除无效地区条件并恢复为“全部地区”，不得留下不可见的筛选状态。
8. 没有任何影视记录时，不显示空的地区选项列表。

### FR-04 地区统计与筛选

1. 选择某个地区后，应显示第一个规范化国家代码与该地区相同的记录。
2. 多国作品仍应完整保存全部国家代码，但只有第一个国家进入顶部地区统计和筛选；第二个及后续国家不生成顶部筛选项，也不匹配顶部地区筛选。
3. 同一部作品在顶部地区统计中最多贡献一次计数。
4. 只有旧数据缺少有效 `originCountry` 时，才从旧中文地区标签回退识别第一个地区；完全无法识别的记录进入“未知地区”。
5. “未知地区”筛选仅包含按本需求第 4 节规则无法识别地区的记录。
6. 地区筛选必须能够与现有影视类型、观看状态、评分、关键词和锁定状态等筛选条件组合使用。
7. 地区选项必须采用以下稳定顺序：
   1. `CN`、`HK`、`TW`、`US`、`JP`、`KR`、`GB` 中实际存在的地区按此固定顺序优先显示；
   2. 其他地区按照当前统计数量降序排列；
   3. 数量相同时按照中文显示名称升序排列；
   4. 显示名称仍相同时按照国家代码升序排列；
   5. “未知地区”存在时始终放在最后。

### FR-05 新记录与 TMDB 数据

1. 新增或更新影视记录时，应完整保留 TMDB 返回的国家代码，包括多国作品的全部国家代码。
2. 电影和剧集可继续使用各自现有的 TMDB 国家字段映射，本次不修改 TMDB 搜索接口。
3. 地区筛选逻辑使用规范化后的国家代码比较，不使用中文显示名称作为主键。
4. 自动生成地区标签时不得覆盖或误删用户自定义的非地区 `contentTags`。

### FR-06 旧数据兼容

1. 旧记录只有 `contentTags`、没有 `originCountry` 时，仍应根据已有地区标签正确识别和筛选。
2. 至少兼容旧版已支持的美国、韩国、日本、英国、中国大陆、中国香港和中国台湾标签及其现有别名。
3. 旧数据中的 `UK` 与“英国”均应映射到 `GB`。
4. 旧数据中的中文逗号、英文逗号、额外空格和重复值不应影响识别结果。
5. 兼容逻辑应在读取或分类层完成，不要求用户执行破坏性数据迁移。
6. 导入、备份恢复和同步得到的旧记录应遵循相同的兼容规则。

## 6. 非功能需求

### 6.1 性能

- 不得明显降低列表初次加载、筛选切换和记录更新性能。
- 地区解析和统计应避免在单次渲染中进行不必要的重复全量计算。
- 不新增运行时在线国家数据请求。

### 6.2 兼容性与稳定性

- 不破坏现有影视类型、观看状态、评分、关键词、锁定状态和排序功能。
- 不修改与地区无关的数据库字段及其语义。
- 新旧记录混合存在时，显示和筛选结果必须一致、可预测。
- 导入、导出、备份、恢复和同步流程不得丢失 `originCountry`。

### 6.3 界面与可访问性

- 保持现有筛选栏的布局、配色、字号和交互风格。
- 地区数量较多时允许换行或横向滚动，但不得遮挡、重叠或挤压其他筛选控件。
- 地区按钮应保留明确的选中状态，并可通过可访问性属性识别。

### 6.4 工程质量

- TypeScript 类型检查通过，不以无必要的类型断言规避错误。
- ESLint 检查通过。
- Vitest 单元测试通过。
- Playwright 相关端到端测试通过。
- 生产构建通过。

## 7. 测试要求

### 7.1 稳定基线回归测试

至少覆盖以下场景：

1. 更新接口拒绝 `createdAt`、`updatedAt`、`id`、`rev` 和 `revActor` 等系统字段。
2. 空更新行为符合 BR-06 规定的明确契约，且不会错误推进 generation 或修改系统时间。
3. 非法数字、数组、对象和未知字段被拒绝，不得写入 SQL `NULL` 或产生部分更新。
4. `updatedAt` 由 Rust 事务生成，前端传入的系统时间不会生效。
5. 更新 SQL 或后续 setting 写入失败时，原有 record、同 ID Tombstone、generation 和相关 setting 均保持不变。
6. 更新不存在的记录时，预先存在的同 ID Tombstone 保持不变。
7. 单个 migration 中途失败时，schema、数据和 `db_version` 整体回滚，之后可以安全重试。
8. setting 不存在与 setting 查询失败能够被区分，查询失败不会被错误解释成默认值或空值。
9. 初始化加载失败显示明确错误和重试入口，不会显示成正常的空列表。
10. 数据目录解析在数据库、日志、海报、备份和 `poster://` 协议之间保持一致。

### 7.2 地区专项单元测试

至少覆盖以下场景：

1. 单一国家代码的规范化、显示和筛选。
2. `FR, DE` 等多国数据的解析、去重、统计和筛选。
3. 小写代码、首尾空格、中英文逗号及重复代码。
4. `UK` 规范化为 `GB`，且新旧写法得到相同结果。
5. `CN`、`HK`、`TW` 分别识别，互不串选。
6. `originCountry` 优先于旧 `contentTags`。
7. `originCountry` 缺失时从旧中文地区标签回退。
8. 国家信息完全缺失或仅含脏数据时归入“未知地区”。
9. 暂无中文映射的有效两位代码能够保留并显示代码。
10. 动态聚合只产生实际存在的地区，并正确计算多国作品数量。
11. 更新 TMDB 地区标签时保留用户自定义标签。

### 7.3 地区专项端到端测试

至少覆盖以下用户流程：

1. 准备包含常见国家、多国作品、`UK` 旧数据、中文旧标签和无国家信息记录的测试数据。
2. 打开列表后，仅显示测试数据中实际存在的地区选项。
3. 分别选择中国大陆、中国香港、中国台湾，列表结果正确且互不混淆。
4. 选择英国时，同时命中 `GB` 新数据和 `UK` 旧数据。
5. 选择多国作品的任一所属地区时，该作品均可见。
6. 选择“未知地区”时，只显示无法识别地区的记录。

### 9.3 R0 专项：“一键补全缺失元数据”安全重构

> 本专项是用户于 2026-08-02 确认并实施的数据安全修复。旧的直接批量覆盖流程已经移除；当前实现先生成预览，确认后仅写仍然缺失的字段，并通过正常记录 action 更新状态及调度同步。

1. 批量任务必须先按记录的电影、剧集和具体季身份生成“缺失字段计划”；没有可靠远端身份的记录应跳过，并显示明确原因。
2. 默认模式只允许写入本地语义上确实缺失、且远端返回值通过校验的字段。已有的题材、地区、评分、状态、媒体类型和内容标签不得被批量任务静默覆盖。
3. 电影时长写入 `movieDuration`，剧集单集时长写入 `episodeRuntime`；剧集或具体季的集数写入 `totalEpisodes`。不得用 `episodeRuntime` 判断电影是否缺失元数据，也不得在电影和剧集字段之间混写。
4. 远端匹配必须校验 TMDB 媒体类型和实体身份。具体季的数据查询及缓存键必须包含剧集实体和季号，不能只使用多季共用的 IMDb ID。
5. 远端没有返回国家、题材、时长或标签时，不得清空本地已有值；地区必须保留完整国家代码，内容标签必须保留用户自定义标签。
6. 写入前必须展示预览，包括待处理记录数、每条记录将补全的字段、跳过原因和潜在冲突；用户确认后才允许执行，并支持安全取消。
7. 执行结果必须逐条区分“已更新、无可补字段、已跳过、失败”，提供原因和可重试范围。总体成功不得只表示数据库写入命令没有报错。
8. 批量写入必须使用正常状态入口或明确设计的原子批量入口，使前端状态、`updatedAt`、dirty/outbox 和自动同步调度保持一致；部分失败不得使已提交数据与界面状态脱节。
9. 外部请求必须有并发限制、速率限制处理、退避重试和可诊断错误，同时不得在日志或通知中泄露凭据。
10. 验收测试至少覆盖：已有字段不被覆盖、电影/剧集/具体季字段映射、远端空值、错误媒体类型、多个季共用 IMDb ID、部分失败、取消与重试、标签与多国家保留，以及成功写入后的同步调度。
11. 所有测试必须使用临时数据库和可控 TMDB mock；不得以真实便携版数据库作为批量补全测试数据。
12. “补全全部字段”限定为 TMDB 可可靠提供的名称、年份、海报、平台、分类、国家/地区标签、TMDB 评分/状态、电影时长以及剧集时长/集数；观看进度、个人评分、备注、观看状态和日期等用户字段不在自动补全范围内。
13. 同一媒体类型返回多个候选时不得自动采用第一条；预览必须列出候选名称、年份、类型及 TMDB ID，由用户明确选择后才读取详情并生成写入计划。
14. 对成功查询后 TMDB 仍未提供值的缺失字段，必须持久记录“记录 ID + IMDb ID + 字段”状态，后续运行跳过该字段；请求失败和未解决的多候选不得记为无数据。IMDb ID 改变、记录删除或状态损坏时必须安全失效/清理。

### 9.4 R1 专项：逐集完成时间与完结状态

> 本专项是用户于 2026-07-29 补充的后续业务需求，属于 DEFERRED；不纳入当前阶段 A、阶段 B 或 `TASK-A-005` 的实现与验收。

1. 适用对象是具有有效 `totalEpisodes` 的剧集类记录。进度选择器采用“下一集待看”语义，依次提供第 1 集至第 N 集，并在第 N 集之后增加“完结”。
2. 当进度从“下一集为第 K 集”前进到“下一集为第 K+1 集”时，系统应把第 K 集记录为已完成，并保存精确完成时间。
3. 当“下一集”为最后一集且用户选择“完结”时，系统应记录最后一集的完成时间，同时把整条记录更新为已看并设置整剧完成日期。
4. 第 1 集没有上一集；首次选择第 1 集不得生成虚假的完成记录。
5. 同一记录、同一集最多只有一条完成记录；重复选择或重试必须幂等，不得覆盖首次非空完成时间或生成重复记录。完成记录允许 `completedAt = NULL`，表示该集已完成但完成时间未记录。
6. 向后调整进度不得自动删除已有完成历史。删除或修正单集完成时间必须是未来专项中明确设计的独立操作。
7. 单集完成事件至少包含稳定事件 ID、记录 ID、集号、完成时间、创建/更新时间；时间持久化使用带时区的明确格式，界面按本地时区显示。
8. 新表 migration、导入导出、备份恢复、WebDAV 同步、Tombstone/冲突策略和旧版本兼容必须在专项实施前定义并测试。
9. 当前 `progress` 是自由文本且历史含义不统一，旧记录不得被静默解释成“下一集待看”。专项必须提供兼容或显式转换策略。
10. **跳集规则（用户于 2026-07-29 确认）**：若从第 K 集直接选择第 M 集（M > K+1），为 K 至 M-2 建立 `completedAt = NULL` 的完成记录，并把第 M-1 集的完成时间记录为当前时间。界面不弹出确认，也不以当前时间批量填充或伪造中间集时间。
11. 单集状态采用三态语义：没有完成记录表示尚未记录为完成；存在记录且 `completedAt = NULL` 表示已完成但时间未记录；存在记录且 `completedAt` 非空表示已完成且时间已知。数据库不得用空字符串或字符串“未知”代替 `NULL`。

#### 已确认的设计方向

- 用户于 2026-07-29 确认采用独立“下一集”模型，不继续把新语义写入自由文本 `progress`。
- 记录表新增可空的结构化 `nextEpisode`；单集完成时间使用独立 `episode_completions` 表，至少包含 `recordId`、`episodeNumber`、`completedAt`、`createdAt`、`updatedAt`，并对 `(recordId, episodeNumber)` 建立唯一约束。
- `episode_completions` 的行存在即表示该集已完成；`completedAt` 可空。没有行表示尚未记录完成，空时间表示已完成但时间未记录，非空时间表示已完成且时间已知。
- 跳集时只为实际跨过的集建立完成记录，不为全部 `totalEpisodes` 预创建行。中间集写 `NULL`，目标“下一集”的前一集写当前时间。
- 更新“下一集”和插入上一集完成事件必须在同一个 Rust/SQLite 事务中完成。任何一步失败都整体回滚。
- 已有非空完成时间默认不可被重复选择或重试覆盖；以后如需修正，使用明确的观看历史编辑操作。
- 从“完结”退回某一集时，可以恢复 `nextEpisode` 并把状态改回“在看”，但不得自动删除最后一集或其他集的已有完成时间。
- 旧 `progress` 保持原样。用户首次启用逐集记录时显式选择“下一集从第几集开始”；不得从 `第12集`、`S01E05`、`完结` 等旧自由文本自动推断或补造完成历史。
- 第一版只覆盖下一集选择、单集完成三态、完结和旧数据启用流程；观看时长、批量补历史、跨季聚合和历史编辑作为后续增强，不进入第一版完成定义。
