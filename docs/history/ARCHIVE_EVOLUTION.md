# WatchTracker 架构演进与技术路线 (Archived)

本文档记录了 WatchTracker 项目在开发过程中的核心架构决策及技术选型演进，旨在为后续维护者提供历史背景参考。

## 1. 技术背景与挑战
项目初期主要面临 Electron 架构带来的三大痛点：
1.  **资源占用高**：Chromium 核心导致安装包臃肿且内存占用大。
2.  **启动延迟**：传统的 `sql.js` (WASM) 方案在冷启动时存在约 1 秒的白屏感。
3.  **构建复杂度**：原生 C++ 模块（如 `better-sqlite3`）与 Electron ABI 的兼容性问题常导致构建失败。

## 2. 核心演进阶段

### 第一阶段：原生驱动探索 (`better-sqlite3`)
-   **目标**：提升数据库查询性能，消除 WASM 转换开销。
-   **结果**：因原生模块在 ASAR 打包环境下的路径加载问题及 CI/CD 环境变量丢失，该方案虽在性能上占优，但维护成本过高，最终被搁置。

### 第二阶段：轻量化替代方案调研
在解决 Electron 痛点的过程中，曾深入调研过以下替代路径：
-   **方案 A (Wails/Tauri)**：利用 WebView2 替代内置 Chromium，以减小体积（~15MB）。
-   **方案 B (Python + Flet)**：利用 Python 生态快速处理抓取逻辑，并使用 Flutter 引擎渲染原生 UI，实现极低开发门槛。
-   **结论**：虽能极致减小体积，但会损失现有的 React 组件资产及丰富的 Web 生态插件，故未最终采纳。

### 第三阶段：最终选型 (Electron 36+ & `node:sqlite`)
-   **核心决策**：利用 Node.js 22+ 内置的 `node:sqlite` 原生模块。
-   **优势**：
    -   **零编译**：内置模块完美解决 ABI 兼容性问题，无需 `@electron/rebuild`。
    -   **瞬时响应**：配合主进程异步初始化及渲染进程骨架屏（Skeleton Screen），实现毫秒级启动。
    -   **生态兼容**：保留了 React 19 + Tailwind CSS 的高效 UI 开发体验。

## 3. 架构经验总结
1.  **UI/IO 解耦**：始终坚持主进程负责 SQLite 操作，渲染进程通过 IPC 通信，确保重型查询不阻塞界面。
2.  **环境自适应**：在便携版开发中，必须处理 Windows `safeStorage` 在不同机器间的解密失效问题。
3.  **极致简洁**：对于个人工具，优先使用系统内置能力（如 `node:sqlite`）优于引入复杂的第三方原生依赖。
